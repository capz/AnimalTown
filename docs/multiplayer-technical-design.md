# AnimalTown Multiplayer Technical Design Draft

The [agreed online play PoC](online-play-poc.md) is the current scope and
execution index. It supersedes this draft's deferred chat/jobs/mail grouping,
raw-TLS-only transport and cloned-card requirements for the PoC. Other broader
release requirements below remain design context rather than additional PoC
scope.

This design covers the first playable GameCube release. A town supports one local villager and up to two guests. The local memory-card save is the source of truth for the town. AnimalTown's hosted service runs the synchronized copy and validates live actions, including visits while the console is off. The Nintendo DOL-015 is the sole hardware qualification target. The agreed PoC also includes live text chat, eligible guest villager jobs and resident mail. [Implementation status](multiplayer-first-slice.md)

## Console connection and game flow

- Add an Online menu alongside the existing Gate travel flow. Keep the existing offline memory-card travel entry. Show distinct states for missing adapter or link, network setup failure, service unavailable, sign-in required, and review or sync pending. Offline play remains available, including while the gate is open online.
- Reuse the short-code entry and browser approval flow. Show the account and town being linked before approval. The displayed code authorizes approval and a separate high-entropy secret proves possession of the original device request. Limit attempts and outstanding requests per account, device, and IP. Replace the existing seven-day account bearer issued by pairing with a scoped device credential. Store it separately from the save payload, assume it can be copied, and rotate it on renewal. Store only its verifier on the server. Relinking or revoking a device invalidates its grants, tickets, and active connections. Keep credentials and pairing secrets out of uploads, URLs, and diagnostics.
- Export a consistent checkpoint from the verified card save. Resolve incremental record references through `SaveRepository` and stream the canonical split records within the 4 MiB limit. Open one authenticated stream for the whole transfer. Reuse a fixed buffer and resume at the last server-verified offset after reconnect. Bind the transfer to its owner, town, branch, parent, and full fingerprint. Recheck authorization and fingerprint at finalization before running split-save validation. Use the same transfer path for later sync and downloads.
- Open the gate after the initial checkpoint is accepted. Use the town's mutual friends list to find open gates. A local villager can close the gate or send one guest home. Closing the gate revokes both visits and resets removals for the next opening. A block overrides an open gate and any existing visit. A guest reconnects to the same seat for up to 60 seconds after the last accepted heartbeat. A disconnected local villager does not close the gate.
- Isolate visiting state from the selected home save. The guest's console renders the host's public town view and gets its own inventory and receipts separately. Save and Quit from a visit returns to the guest's home flow. Save operations in a guest session never write the destination town to the home card.

The entry points are `Program.RunTown`, `RunSession`, `TownSession.Load`, the Gate UI, and the existing card save path. Introduce an online session mode alongside solo and card travel. It owns the connection, snapshot application, and action queue. Local controls use the same gameplay rules in both modes. An online action produces a server command before the console applies a persistent change. ## DOL-015 transport

Use outbound IPv4 with DHCP or explicit IPv4 configuration. For the PoC, use HTTPS for account/gate requests and secure WebSockets (WSS) through a free Cloudflare Quick Tunnel for gameplay. Add bounded WebSocket framing over the SDK TLS stream and a server upgrade endpoint, carrying the existing versioned binary protocol. The console negotiates HTTP/1.1 with the Cloudflare edge rather than the experimental raw listener's `animaltown/1` ALPN. A temporary tunnel supplies the public hostname; no purchased domain is required. Preserve hostname, chain and date validation, fresh entropy and credible console time. Fail closed if secure setup fails. Qualify this route on Dolphin and physical DOL-015 before treating it as working transport. See the [transport contract](online-play-poc.md#cloudflare-transport-contract) for endpoint changes and authentication.

Use one active TLS connection on the console. Reuse an authenticated stream for live play and for transfers in an explicit loading or save mode, or close it before opening a transfer stream. Suspend regular rendering and release scene resources before bulk card work or a cold resnapshot. Keep only essential control traffic active during a transfer. The SDK HTTP client closes each request and has no session resumption, so one HTTPS request per page would repeat the full handshake. [SDK pin](../game/AnimalTown.GameCube/packages.lock.json) · [SDK networking](https://github.com/capz/DolphinDotNet/blob/main/docs/network-runtime.md) · [SDK TLS](https://github.com/capz/DolphinDotNet/blob/main/docs/https.md) · [SDK entropy](https://github.com/capz/DolphinDotNet/blob/main/docs/platform-entropy.md)

Use compact little-endian frames with message type, version, and payload length. Validate type-specific lengths before decoding. Start with a 4 KiB upper cap for bulk pages, 64 B for a movement payload, and 16–32 KiB total game protocol staging for queues and buffers. These are spike budgets. Preallocate buffers and use one latest-wins slot per actor for unsent movement. Start at 20 Hz input and 10 Hz position updates. Cap receive and apply work per frame by bytes, event count, and elapsed time. Keep reliable events ordered and use backpressure followed by bounded replay or resnapshot when a client falls behind. Test TCP head-of-line stalls and recovery under latency and loss.

Enforce per-device, account, IP, and service-wide limits on connections, ticket issuance, uploads, and retained bytes. Rate-limit authenticated and unauthenticated traffic before expensive work. Give handshakes, partial frames, and upload staging progress deadlines. Bound complete snapshots, replay windows, and object counts as well as individual frames. Expire incomplete transfers and stage them within a server-side storage quota.

The server commits gameplay mutations with their event and receipt before acknowledging them. Reconnect carries the last applied event sequence and a fresh ticket for the same seat. The server replays missing reliable events or sends a paged snapshot at a fixed event watermark. The client applies subsequent events in order and refreshes on a gap. Serialize snapshots and replays from a per-recipient allowlisted projection. Check current membership and room visibility before sending data. Guests receive public map and room data, permitted objects and actors, and their own inventory or receipts. Keep private inventory, mail, account settings, and card contents out of the guest projection.

## Hosted session and live movement

Use a single writer per hosted town. PostgreSQL stores gate state, visit seats, checkpoint lineage, pending reviews, and durable operations. A lease and increasing epoch fence a replaced worker or transport connection. A parked open town can release its in-memory worker and reopen from its checkpoint and journal on demand. Route existing inventory, shop, grant, and town mutations through the same writer or reject them for a managed town. Check current account, villager generation, seat, epoch, gate membership, and review state in the transaction that commits each durable change. Bind idempotency keys to the actor, action, and canonical payload. Return the stored outcome for the same request and reject a key reused with a different payload.

Bind each seat to the town account, persistent villager identity and generation, and session epoch. Issue single-use, short-lived gameplay tickets scoped to the service, town, seat, villager generation, and session epoch. A new connection consumes a fresh ticket and invalidates the previous connection for that seat. The owner seat is separate from the two guest seats. Active and reserved guest seats both count against capacity. On reconnect, a guest sees the current review state before accepting movement input. Close, kick, and block revoke access before allowing further mutations.

The server validates normalized movement input against canonical speed, collision, and portal rules. The client predicts its own movement and corrects it using the last input acknowledged by the server. Render the two remote humans from a bounded interpolation buffer. Charge their instances, pose updates, and shadows against the existing actor and model-residency budgets. Share species models and texture resources with existing actors. Start with a measured pose update cadence and qualify both guests visible with distinct species alongside NPCs. Human roster and appearance data stay separate from the NPC actors and offline visitor capsules. Guests can enter villager homes through validated portal transitions. The server sends both the room and position on transitions and initial spawn. Obtain a fresh town snapshot after a failed transition or incompatible reconnect.

## World actions and item ownership

| Action | Server behavior and review |
| --- | --- |
| Place an item | Validate the guest's pocket, current space, reach, footprint, and inventory revision. Debit the item and create a stable placement ID owned by that villager. The placement becomes one pending review entry. |
| Move or rotate | Validate the same space and ownership rules. Update the existing placement and its final position, rotation, and room. |
| Pick up a pending placement | Only the placing villager can pick it up. Return the item to their pockets and remove the review entry in the same transaction. If the pockets are full, preserve the placement and its ownership. |
| Dig a hole | Record a terrain change with a stable cell reference, guest identity, and visit ID. Keep game-buried item recovery in a separate durable receipt. |
| Pick up a game-spawned item or recover a game-buried item | Validate the object's game-spawn provenance and award it once in the hosted copy. It stays recovered if the associated hole is cleared. |
| Buy from the shop | Commit stock, debit, and inventory or delivery receipt atomically. Confirmed purchases are permanent. Player-owned listings use escrow, with one shared inventory of listings across the physical stands and legacy listing API. |

Server-authorized identities and expected object versions govern edits. Compact array indices stay local to the implementation. Keep item lineage and hole records in versioned state. Assign existing item IDs once at the first synchronized checkpoint, then write them back with the card records so both copies share the same IDs. Allocate new offline objects under their card branch ID and new hosted objects under the hosted town ID and epoch. The existing shovel action uses a buried-item marker, so the new data distinguishes a visible hole, a game-spawned buried item, and an item placed by a player. Older records with ambiguous origins retain their saved behavior until they can be classified reliably. A guest cannot mutate pre-existing possessions or claim anything from the koban. A reviewed item held at the koban has no guest ownership. [Current item rules](../shared/AnimalTown.Domain/TownItemActions.cs) · [Existing shop transactions](../server/AnimalTown.Server/TownShop.cs)

## Owner review and interruption

A local villager starts review on entry after unattended guest play, or as they leave after shared play. The server serializes the review boundary with gameplay. Freeze guest simulation and reject new guest commands during the review. Keep the connection and heartbeat alive while showing the waiting screen. The reviewer sees each pending placement once at its latest position and rotation. The options are **Keep in town** and **Send to koban**. The hole entry groups all remaining holes dug by one visitor during one visit. A single decision clears that group while preserving recovered items. The review can include offline conflicts as described below.

One decision commits at a time with an operation ID and the expected version of the entry. A keep transfers the item to the town. A removal transfers it to the koban and preserves exactly one item. Use bounded deferred custody when the ordinary koban storage is full. If neither storage path can receive an item, leave the review row pending and surface the capacity issue. Commit the decision, transfer, and receipt together before reporting success.

During a review, a short liveness lease controls the pause. Release the pause on an explicit end or confirmed disconnect, with a provisional ten-second expiry for a silent loss. Committed decisions stand. Guests resume and can move or retrieve their remaining placements. The next local villager resumes review using the latest server versions, with retrieved placements gone. New changes after an interruption are collected for the next review. Guests can also continue visiting after a normal review and the local villager's departure.

## Offline reconciliation and card recovery

The service keeps every town's last shared checkpoint and the durable actions committed since it. Each card sync presents a server-issued parent checkpoint and branch reference plus an export fingerprint. Treat them as lookup inputs and validate lineage against server state before accepting any change. The server detects two local copies with divergent progress and asks the player which branch to continue from. The chosen save remains the basis for local progress. Reconcile it with guest edits and permanent online receipts. Upload retries reuse their prior result.

Reconciliation compares the base checkpoint, selected local save, and hosted journal. Accept validated local items, balances, and offline progress. Keep online receipts, escrow, claim status, and online item provenance server-authoritative across branches. Card-supplied fields cannot create or revoke those records. Apply compatible changes, then ask the local villager to choose any conflict between a guest edit and their offline action. Match stable identities and occupied footprints in the same room. Include terrain or building changes that invalidate a placement. If a local placement wins, send the conflicting guest item to the koban. If a guest placement wins, send the displaced local item there. A set of overlapping placements is one conflict so that either choice leaves a valid world. Revalidate each choice against the live revision and ensure all needed koban transfers can fit before committing. A cleared hole only affects the recorded hole instance. It cannot clear a replacement created later on that cell.

Give every permanent transaction a stable server receipt and track application per branch. A card cursor reports progress for a verified checkpoint. It never grants authority to mint or redeem an online effect. Bind application to the checkpoint and selected branch on the server. An online purchase or game-spawned recovery can be granted once to the appropriate recipient. Reconcile an already bought game-stocked slot to sold out while both players keep their purchases. Use spawn-cycle IDs to prevent a consumed game-spawned object from reappearing through a stale snapshot. Keep the permanent effect even when a related reversible terrain or placement change is undone.

Before an online listing is activated, durably stage the transfer on the card and move the item out of spendable inventory. Retry the listing with the same ID. The online sale or cancellation yields a receipt applied once on the next card sync. Apply the same card-first reservation idea to a proposed guest travel backpack and spending balance so the same card cannot offer the same items or Bells for simultaneous online and offline use. A copied older card still requires normal branch selection and reconciliation. Preserve committed online receipts and never release the same escrow item twice. If the selected branch lacks enough Bells or contains a conflicting use of the same unique item, keep the affected settlement pending and show the conflict. Offline play remains available. Keep affected online commerce disabled until a deterministic settlement rule covers these cases.

Keep a durable pending sync marker on the card. Each sync records the parent checkpoint and a server event watermark. While review is active, serialize approved changes into the hosted journal so guests see the same outcome when they resume. The server prepares an immutable checkpoint plus its receipt cursor. Pin it until the card confirms publication or the local player explicitly resolves a competing branch. A retry can use the same checkpoint even after guests resume. The console verifies the complete checkpoint and publishes it through `SaveRepository`'s bank and manifest readback before acknowledging that cursor. If power fails before publication, the old bank remains the local source of truth and the pending checkpoint can be retried. If the card publishes and the acknowledgment is lost, the console resends the same receipt. If the card is full or removed, keep the server checkpoint and unapplied deliveries available. Server changes after that checkpoint's watermark remain in the next sync.

## DOL-015 resource and acceptance budgets

- Keep the existing 6 MiB managed heap and preserve the save path's approximately 1.63 MiB contiguous allocation under maximum economy load. Reuse bulk and snapshot staging after the scene unloads. Compare networking-enabled and baseline DOL sections and measure main RAM at runtime. Account for linked code and BSS, native stacks, socket pools, TLS records and handshake peaks, and any retained UDP staging used by DNS. The 16–32 KiB staging target applies only to game-owned protocol buffers. [Existing save memory measurements](villager-jobs-offline-implementation.md)
- Target zero steady-state network allocations and at most 1 ms added p95 frame time during live play, including both remote actors. Record p99 and maximum frame times, longest single network operation, missed retraces, minimum free MEM1, managed live bytes and largest free block, native allocation peaks, and model, texture, and ARAM residency. Derive total networking and actor budgets from a matched physical baseline before enabling them together.
- Compare the same dense winter town in solo play and with two guests on the DOL-015. Include both guests and NPCs in view, water and effects, cold room transitions, cable pull and reconnect, maximum card transfer and publication, and an extended session. Use lightweight counters for the first comparison and verify that shedding optional residency or abandoning a stalled transfer returns the allocation headroom. Adjust transport work and guest rendering inside the existing memory budgets if the spike misses its targets.

## Proposed implementation order and acceptance

1. **Target spike and SDK integration.** Bring up an actual DOL-015 connection through DHCP, TLS, pairing, a small checkpoint transfer, and simultaneous movement samples. Measure frame time and managed and native memory under a dense scene, worst-case checkpoint transfer, reconnect, and an interrupted connection. Use Dolphin for repeatable development coverage. Qualification requires the physical DOL-015.
2. **Hosted visit and console integration.** Add the online lifecycle, one local and two remote humans, room transitions, streamed snapshots, and reconnection. Verify cross-endian protocol fixtures, malformed frame rejection, stale session fencing, membership revocation, and correct save routing.
3. **Durable gameplay and live review.** Wire placement, pickup, holes, and shopping through the command path. Test concurrent purchase winners, retries after commit before reply, review interruption after any decision, older review versions, guest pause and resume, and koban capacity failures.
4. **Card reconcile and release.** Test the two offline branches, both choices of a placement conflict, the same finite stock slot bought twice across branches, escrow across a restart, and card failure before and after manifest publication. Complete a three-human session and reload the local card on real hardware. Include the matching ISO and standalone SD application in a release candidate.

## Decisions for review

1. **Connection parameters.** Use HTTPS for account and gate calls and one authenticated stream for live gameplay or bulk transfer at a time. Confirm shipping rates, total memory budgets, and liveness timeouts from physical measurements.
2. **Guest spending and stale copies.** Reserve a travel backpack and spending balance on the home card before joining. If the player later chooses an older branch that already spent some of that value, the proposed behavior is to preserve completed online purchases and hold the conflicting local inventory or wallet settlement for an explicit reconciliation choice. Define the exact resolution if the local wallet cannot cover a committed debit or both branches consumed the same unique item.
3. **Review after startup or exit.** Enter review during the return-to-title flow after shared play and before resuming the town after unattended play. An unavailable service leaves review pending and allows offline play.
